Assess existing evidence before delegating: accept focused owner proof after root inspection for bounded fixes; independently verify initial changes, material behavior changes or uncertain applicability with Sol/high per [profile routing](../poteto-mode/references/claudep-routing.md). Give the verifier expected behavior, exact base/head, scoped scenarios and existing proof; run only missing or invalidated checks. A worker already on the configured model/effort verifies directly. Before a paid or long run, prove keys, memberships, flags, runtime versions and fixture sizes reach it, and check the scorer on one known pass and one known fail.


1. Derive scenarios from the change's real producers, consumers and state transitions, and run them on the change merged with current main; a green suite on the head alone is not proof. Define expected behavior, entry point and side effects. Prove it through the running API, worker, CLI or actual browser UI. Compare bugs on equivalent failing-base and fixed-head fixtures, and refactors on matching base/head scenarios and side effects; label missing baselines. Cover happy paths, common failures, handled edge cases and, when relevant, permissions, compatibility, regression paths, flag states, old/new records and affected product modes. Record each scenario's inputs, expected outcomes, evidence and pass predicate. Measure performance when the path is performance-sensitive or has an agreed budget; otherwise record why it is unnecessary. Through the running entry point, prove allowed access, same-org other-user denial for user-scoped data, and cross-org denial for tenant-scoped data; check denied responses expose no protected content. Focused tests support runtime checks. For shared-code changes, refactors and lint migrations, use [behavior review](references/behavior-review.md) to map affected entry points to expected effects and evidence in the existing verification report.
2. Reassess after babysitting and each head/base change; rerun only missing or invalidated checks, reusing applicable owner, verifier and CI results. Assess applicability across code, dependencies, base, environment, fixtures and scenario inputs. Reuse unaffected proof only with the compared diff named, and rerun changed or uncertain behavior. Give follow-up verifiers the exact scenarios to rerun and evidence to reuse; retain original tested revisions and outstanding limits. Keep tested revisions separate from assessed revisions, verify stack layers with ancestors only, and satisfy required CI.
3. Use the project's documented local runtime and health checks, or its project verification skill, for private checkouts, configuration and owned service slots. Run the project's health check before and after new service evidence, and run base and head side by side when the scenario compares behavior.
4. Exercise the relevant entry point: API requests with responses and persisted effects; worker jobs with correlated completion, output and side effects; CLI commands with exit status and actual output/files. Confirm expected outcomes and relevant errors; inspect generated/downloaded artifacts and relevant UI transitions when those are in scope. For UI checks only, follow [browser](references/browser.md), [capture](references/capture.md) and [video](references/video.md) for native computer use, owned-window recording and reviewed edits. UI checks are only accepted when the user has explicitly requested them; API, worker and CLI checks need none of the UI references.
5. Follow [evidence and delivery](references/evidence.md). Fix findings within the authorized scope, then report verified, partially verified or blocked, copying the verifier's label word for word, with tested revisions, fresh/reused/untested checks, later fixes and limits. Only verified passes a gate; label an infrastructure stop as blocked. Record fresh proof with `scripts/verdict.py record`; carry forward applicable proof with `scripts/verdict.py carry-forward --record <prior.json> --head <current-head> --base <current-base-sha> --base-branch <current-base-branch> --reason <applicability-reason> --out <new.json>`, preserving its label and measurement, and run `scripts/verdict.py check --claim <claim>` before any summary, status line or gate uses it. When authorized, publish a new PR evidence comment with GitHub attachments. Release owned resources, restore local gates, remove ephemeral credentials and apply the evidence retention policy.

Report code confidence and review-bot status as separate fields, state live and video status beside each rating, and re-rate only when code changes.
