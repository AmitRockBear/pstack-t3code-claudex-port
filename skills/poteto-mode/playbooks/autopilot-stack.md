### Autopilot-stack

**You own the stack, never the landing. Hand the operator one linear stack of base-chained PRs to review and land.** **Autopilot-full** holds except for how verified work leaves. Each authorized tick re-reads both installed playbooks, and this one wins where they differ.

In T3, follow [Babysit's parent-owned PR watches](babysit.md): owners return after finite build or comment-fix work, and the root assembles readiness from their receipts, existing verification and PR wakes. Use `delegate_task` for a new finite fix assignment when a wake requires work.

During T3 child audits, use [profile routing's status and pending-question checks](../references/claudep-routing.md#ownership-and-completion) before classifying a lane as stuck.

Owner and reviewer briefs:

- Keep current cross-lane decisions in the program's existing `<program-output>/root/amendments.md`, with affected lanes, scope, reason and evidence; keep historical decisions in `decisions.tsv`.
- Paste the review standard from `~/.pstack/skills/babysit/SKILL.md` verbatim into every owner and reviewer brief, from "For each review comment, check" through the diminishing-returns rule.
- Include the absolute amendments path and relevant accepted decisions in every owner and reviewer brief; require rereading that file before each phase or review round.
- Include the absolute [profile routing](../references/claudep-routing.md) path in every brief and require owners to pass it to their helpers. Dispatch explicit-effort Claude and Sol helpers through `delegate_task` with their role-specific models and explicit effort options, then check each returned `childThreadId` with `t3_thread_configuration` before relying on the helper's result.
- Notify affected active owners and reviewers when an amendment changes and confirm they read it before dependent work; use `t3_thread_send` with `mode: "steer"` for an in-flight T3 child update. Start a new delegated review round with `delegate_task` and its full review context.
- Complete each required review at the phase named by the plan or invoked skill before advancing; record the authorization for a changed review phase.
- Label coordinator choices as coordinator decisions; cite the actual user message when claiming the operator requested an exception.

1. **Run the owner workflow.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for PR create, edit, view, watch, and merge operations. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One background subagent per PR, in its own worktree, owns its change end to end: build, first push, a ready PR opened only after implementation and focused development checks are complete, skeptical review-bot triage per `../references/bugbot-triage.md`, PR cleanup per [Opening a PR](opening-a-pr.md), and, outside T3, babysit to green per `playbooks/babysit.md`. In T3, the root owns babysitting and delegates finite fixes as needed. Owners run required pre-push checks and focused development checks on the affected behavior. They hand commands, fixtures, exact revisions, and available receipts to the designated independent Sol 6.1/high verifier. That verifier owns complete scenario coverage and the verification report. Follow [verify-change](../../verify-change/SKILL.md) for verification procedure and evidence assessment. Owners parallelize when the work is self-contained. A dependent item starts from its parent branch. Owners never rebase onto another branch, trunk included; the root owns topology. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill. Open the PR only after implementation, PR cleanup, required pre-push checks and focused development checks are complete. After each completed verifiable unit, run its focused checks and push the authorized task branch with hooks on; report the exact SHA and reuse applicable evidence. Push the completed head and open the PR ready, never draft, then begin independent verification and babysitting. Keep the trail uncommitted and return it in the report. Owners also keep the `children.tsv` of Autopilot-full step 2.
2. **Audit on the wake chain.** The root runs an audit tick hourly. In T3, use the parent-owned persistent schedule in profile routing. Outside T3, use the host's supported `/loop 1h` wake mechanism. Never leave the cadence to memory or lossy completion notifications. At each tick, re-read this playbook from disk (`skills/poteto-mode/playbooks/autopilot-stack.md` under the installed plugin), then re-read the standing objective. Audit the operation against both. Fix drift during that tick. Probe each owner with a generic liveness or status check. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that passes its expected runtime without a side effect as stuck. Stand it down and dispatch a replacement at once. Do not wait for a polite return. Probe all subagents and end the tick per Autopilot-full step 6.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On the operator's explicit go, write the full program objective into the standing orders and restate it in your todolist. That objective stands across turns until the chain is done. On the operator's stop, every owner takes an immediate zero-writes hold.
4. **Verify each round.** The owner reports its code-ready head SHA once the shipped code is final. Outside T3, it reports STACK-READY with the exact head SHA when its loop is green; in T3, the root assembles STACK-READY from the owner's finite receipt, current-head checks, reviews and verification. Record each verdict with `~/.pstack/skills/verify-change/scripts/verdict.py record`, and treat it as clean only when `verdict.py check --claim verified` exits 0 at the current PR head. Record each verdict's head SHA, base SHA, base branch, and stable base-to-head patch-id so later rewrites can be compared with the reviewed context. The root applies Autopilot-full step 4 and [verify-change](../../verify-change/SKILL.md), reusing applicable layer proof and checking only integration boundaries affected by parent changes. Give each layer's verifier its exact base/head and an ancestor-only checkout; report integrated-stack checks separately under [Evidence and delivery](../../verify-change/references/evidence.md). Use STACK-READY in place of merge-ready. Nothing enters the stack unverified.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. A clean verdict appends the PR to the one linear base-branch stack, in verified order or an order the operator specified.
6. **Single writer on topology, parallel writers on builds.** Owners push only their own branches and report the tip, current base, and intended parent. The root is the only topology writer. Before any rewrite or retarget, read [Merge and restack safety](../references/merge-safety.md) and restack with its `restack.sh`, then follow it: capture the affected chain and remote heads, cancel both auto-merge requests and queue membership for that chain, and verify cancellation. Leave unrelated PRs alone. To append a PR, fetch the intended parent, rebase the child branch onto that exact parent tip, push with `--force-with-lease=refs/heads/<branch>:<captured-remote-head>` using the remote SHA captured before rewriting, and set the PR base to the parent branch. Create it with `origin pr create --status open --base <parent-branch>` or `gh pr create --base <parent-branch>` according to the resolved forge. Retarget an existing PR with `origin pr edit <pr> --base <parent-branch>` or `gh pr edit <pr> --base <parent-branch>`. Only the root PR targets trunk. Never submit or register the chain through `gt`.
7. **Refresh trunk only when needed, then reassess affected evidence.** The root fetches `origin/main` and rebases only when a branch conflicts with it or must incorporate a relevant change from it. Do not rebase on a timer just to stay current. When a trunk refresh is needed, the root rebases the affected chain from bottom to top. When a rebase surfaces conflicts in an owner's files, that owner fixes its own slice and the root pushes the result. A rewrite invalidates readiness at affected heads. Reassess each affected verdict under [verify-change](../../verify-change/SKILL.md) and the patch-id rule in `playbooks/shipping.md`, including applicability to the new base and context. Complete that assessment through step 4 before delivery; an equivalent restack requires a current assessment, not another verifier. Re-run mergeability and CI after every rewritten push even when the patch-id is unchanged. The countersign rule is unchanged from Autopilot-full. A genuinely new pin raises a stop for the root's fresh countersign. Absorbing drift of landed values is not a raise.
8. **Deliver the chain, then leave landing to its owner.** Once landing starts, no one writes to the chain except the post-merge retarget allowed by [Shipping](shipping.md). Report a mid-landing problem to the operator and wait for authorization before a fix. The deliverable is one linear chain of verified PRs, reviewable bottom-up in the resolved forge, every link carrying its verifier verdict in the PR body or a comment. The operator reviews and lands it, with their own clicks or by arming merge-when-ready.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** catch the operator up per the **ketchup** skill, with links to the stack root and tip, a one-line verdict per link, and anything parked or excluded with the reason.
