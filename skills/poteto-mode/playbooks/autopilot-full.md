### Autopilot-full

Resolve the driver skill through [poteto-mode's Non-negotiables](../SKILL.md#non-negotiables).

In T3, follow [Babysit's parent-owned PR watches](babysit.md): owners return after finite build or comment-fix work, and the root assembles readiness from their receipts, existing verification and PR wakes. Use `delegate_task` for a new finite fix assignment when a wake requires work.

During T3 child audits, use [profile routing's status and pending-question checks](../references/claudep-routing.md#ownership-and-completion) before classifying a lane as stuck.

**You own the verdicts, never the PRs. One owner runs each PR from build to merge-ready, and nothing merges without both your clean verification verdict and the operator's explicit merge click.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle up to merge-ready, the operator clicks the merge, and the root keeps verification, countersigns and audits, plus PR watches in T3.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go. On that go, write the full program objective into the standing orders and restate it in your todolist. That objective stands across turns until the queue is done.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for PR create, edit, view, watch, and merge operations. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One background subagent per PR, in its own worktree, owns build, the first push, a ready PR, skeptical review-bot triage per `../references/bugbot-triage.md`, PR cleanup per [Opening a PR](opening-a-pr.md), a conditional rebase onto `origin/main`, and, outside T3, the babysit loop to green (`playbooks/babysit.md`). In T3, the root owns babysitting and delegates finite fixes as needed. Owners run required pre-push checks and focused development checks on the affected behavior. They hand commands, fixtures, exact revisions, and available receipts to the designated independent Sol 6.1/high verifier. That verifier owns complete scenario coverage and the verification report. Follow [verify-change](../../verify-change/SKILL.md) for verification procedure and evidence assessment. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill. Open the PR only after implementation, PR cleanup, required pre-push checks and focused development checks are complete. After each completed verifiable unit, run its focused checks and push the authorized task branch with hooks on; report the exact SHA and reuse applicable evidence. Push the completed head and open the PR ready, never draft, then begin independent verification and babysitting. Keep `decisions.tsv` uncommitted and return it with the reports. As soon as a subagent starts, the owner adds its ID, expected runtime (at least the longest past run of that kind), and state to a `children.tsv` kept the same way. The owner rebases only when the branch conflicts with `origin/main` or must incorporate a relevant change from `origin/main`. Do not rebase on a timer just to stay current. After a rebase, reassess evidence under [verify-change](../../verify-change/SKILL.md). When the shipped code is final, after PR cleanup, it reports the code-ready head SHA. It also reports the SHA of each later push that changes the patch. CI and babysit then run in parallel with independent verification. Outside T3, the owner reports merge-ready with the head SHA when focused development checks, CI, and babysit finish. In T3, the owner returns its finite work receipt and the root determines readiness from current-head CI, reviews and verification. Before a push that starts a round, run the pre-review checks that the repo's CLAUDE.md files and rules name for the touched paths. Run them on the committed head. A hook pass is not proof. To publish each rebase, push only the owner's branch with `--force-with-lease=refs/heads/<branch>:<captured-remote-head>`, pinned to the last SHA that owner pushed or took over; report an unexpected remote head to the root. Never force-push a shared branch. The owner drives to merge-ready and stops there. No owner runs the merge. Step 4 gates the verdict and step 5 hands the merge to the operator.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Self-contained PRs branch straight off main, and sequenced work is merge-then-branch. One exception: an owner that must split a genuinely dependent change may hold a short private base-branch stack.
4. **Verify each round before its merge.** Independently verify the first code-ready head; for later pushes, the root applies [verify-change](../../verify-change/SKILL.md), carrying forward applicable proof and commissioning only justified follow-up work. The verifier did not write the code. Declare each round's applicable risk cases under [Multi-phase plan's audit policy](multi-phase-plan.md). Initially run one independent read-only source audit and a second for those five cases; repeat audits only for affected findings or new risks. The first auditor checks the risk declaration against the diff and reports missing cases. The root updates the declaration and obtains the required second audit before a clean verdict. The second auditor has a distinct focus on the applicable risks. Both read the full brief, diff and verification receipts and did not write the code. The root reviews the receipts and aggregates one verdict at the recorded head and base. No merge without the root's clean verdict. Send every proven finding to the owner in one fix-forward, including defects reported as notes. For each behavior finding, ask for a red test covering the affected sites, or a repro receipt when no test can show the defect. Add the defect to the next round's brief. Reassess later revisions under [verify-change](../../verify-change/SKILL.md) and [Shipping](shipping.md).
5. **On a clean verdict the owner hands off and takes the next item.** Merge prep never comes before a round's lanes start. At merge prep, fetch `origin/main`, check mergeability and whether a relevant trunk change is required, and rebase only under step 2's rule. After a rebase, the owner reports the new head SHA. A new head invalidates readiness. Apply [verify-change](../../verify-change/SKILL.md) and the patch-id applicability rule in [Shipping](shipping.md). An unchanged patch-id may preserve substantive review only after checking its applicability to the new base and context. Rerun required CI and mergeability on the current head before hand-off. If trunk moves again before the operator merges, reassess applicability and apply the same conditional rebase rule; trunk movement alone does not require a rebase or full verification. The owner presents the verified merge-ready PR to the operator, with its verification verdict and pinned SHA, then picks up its next self-contained item from the queue. The operator reviews and squash-merges. No owner runs the merge itself. Every item waits for the operator's click, the gate operator-named items always had. The root's clean verdict is a precondition for that click, never a substitute for it.
6. **Run the root layer.** Any change that loosens a gate, such as a raised budget or an allowlist entry, needs verifier proof and the root's fresh countersign. Where the user's grant covers approval, record that countersign for a lane to check. Restore any check that the patch disables or soft-fails. Never give or bypass an approval the forge enforces. Absorbing values already on main is drift, not a gate change. Run an audit tick over all owners hourly. In T3, use the parent-owned persistent schedule in profile routing. Outside T3, use the host's supported `/loop 1h` wake mechanism. Never leave the cadence to memory or lossy completion notifications. At each tick, re-read this playbook from disk (`skills/poteto-mode/playbooks/autopilot-full.md` under the installed plugin), then re-read the standing objective. Audit the operation against both. Fix drift during that tick. Probe each owner with a generic liveness or status check, and collect the decision trails. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that errors, cannot start a turn, or passes its expected runtime without a side effect as stuck; answer pending parent or user questions before classifying a waiting lane as stuck. Have owners record missing heads or child IDs before treating that record gap as a stall. Stand it down and dispatch a replacement at once. Do not wait for a polite return. Each tick also runs the lane stuck test over the program's agent list, where the platform has one, and over every owner's `children.tsv`. Whether or not a stop works, the root has the owner record each stuck subagent as stuck and, if its work is still needed, replace it. Each replacement that stalls gets the same steps. The root takes both steps when the owner cannot. A stall never proves or drops the work. When merges batch, run a retro pass and a post-merge bot-comment sweep. Consume available results and pending questions, then yield when only owned children remain. Stop supervision only after all owned child work and the program's completion checks are settled. Use **ketchup** when a tick changed something for the operator; keep unchanged ticks quiet.
7. **Stand down instantly on the operator's stop.** The operator's hold or stand-down reaches every owner as a zero-writes order immediately. Owners hold their briefs until the operator releases them.

**Reply:** catch the operator up per the **ketchup** skill, covering the queue with each PR's owner, state, and head SHA. Each verdict and the scenarios and audits that produced it. What merged and what each owner took next. Countersigns granted and why. Open operator gates. Where the collected decision trails live.
